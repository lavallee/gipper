How gipper chooses an offer

Code: gipper/costs.py (the estimate and score), gipper/history.py (memory), gipper/market.py (filters and order), gipper/placement.py (the job's hints).

The order

  1. Filters. Enough GPU memory; inside [gpu] regions; UDP if a port asks for it; at or under max_usd_per_h; expected cost within [budget] max_usd; and any [placement] floor the provider advertises (min_host_download_mbps, min_host_upload_mbps, min_cuda, min_compute_capability). A floor the provider doesn't advertise passes the filter and is checked on the machine itself. Runpod doesn't advertise compute capability, so a Runpod GPU below min_compute_capability is rented and then rejected; use prefer or providers to avoid that.
  2. prefer, in the job's order. GPUs it doesn't list come after all the ones it does.
  3. Known stock first. Runpod GPU types without reported stock mostly fail to rent; Vast and Shadeform offers are specific machines, always in stock.
  4. Score, lowest first.
  5. The provider order in settings, as a tie-break.

The estimate

wall     = ready + setup + upload + fetch + compute + download
expected = (wall x $/h + bandwidth fees) x billing factor
risk     = p_fail x (failure_cost_usd + (ready + 60 s) x ($/h + hour value))
score    = expected + risk + hour value x wall
Figure First choice Then Then Default
ready memory: median for this machine median for the provider Runpod 90 s, Vast 120 s, Shadeform 420 s
setup placement.setup_s 120 s
upload placement.upload_gb (else the size of [[inputs]]) over the measured link to this machine to the provider advertised host download × transfer_efficiency 100 Mb/s × efficiency
fetch placement.setup_download_gb over the advertised host download × efficiency 100 Mb/s × efficiency
compute compute_s_by_gpu for this GPU --throughput with units.count placement.compute_s memory: median for this workload on this GPU, else 30 min (capped at max_hours)
download placement.download_gb over the measured link back advertised host upload × efficiency 100 Mb/s × efficiency
bandwidth Vast's advertised $/GB in and out Runpod: none charged. Vast without advertised fees: 0, flagged bandwidth_known: false
billing factor memory: billed ÷ computed for the provider, totals over rentals of 10 minutes or more (shorter ones mostly measure rounding) 1.0
p_fail the machine's record, weighted 2 rentals towards the provider's rate the provider's record, weighted 4 rentals towards 10% 10%

"Measured" links come only from timed real transfers of 20 MB or more (inputs going up, outputs coming down when the job doesn't checkpoint them). The optional probe never counts: a 2 MiB probe mostly measures ssh start-up, so it reads low.

gipper pod estimate JOB prints the phases, the dollars, the risk and, under "from", where each figure came from. The estimate receipt records all of it.

Real-time work

[placement]
profile = "interactive"                         # objective defaults to "latency"
latency_target = "interactive-client"          # where the RTTs below were measured from
measured_rtt_ms_by_machine = { "vast:machine:12345" = 28 }
max_rtt_ms = 50                                 # unmeasured offers fail this
preferred_countries = ["CA", "US"]
near_latitude = 43.65                           # with max_distance_km: offers without
near_longitude = -79.38                         # coordinates fail it
max_distance_km = 1500

After prefer and stock, offers rank by the best round-trip figure there is (offers with one first, lowest first), then by position in preferred_countries, then by distance, then by the usual score. The figure comes from, in order of trust:

  1. the job's own measured_rtt_ms_by_machine, measured from latency_target;
  2. a ping from this machine just before renting (probe_rtt, on by default for interactive jobs; up to the 48 cheapest hosts; hosts that do not answer have no probe measurement);
  3. memory of that machine's round trip from here (host.rtt on every rental, market.rtt from earlier pings);
  4. the median round trip from here to hosts in its country.

Only 1 counts as measured for max_rtt_ms, unless latency_target = "here" (the user is at this machine), when 2 counts too. Otherwise 2–4 are proxies: they rank offers but can't pass the limit.

Country is the roughest proxy. Provider labels may be inaccurate and are not a substitute for measurements from the client that needs low latency. Vast does not expose coordinates through this adapter, so a max_distance_km limit currently leaves no Vast offers.

Batch jobs (any objective but latency) ignore all of this. A cheap host on the other side of the world wins whenever the whole run costs less; its slower transfers are priced from link-speed memory, which is kept per country.

Other fields

  • min_dlperf: a floor on Vast's DLPerf, a generic provider score. It filters offers; it is never read as this workload's speed.
  • client_upload_mbps / client_download_mbps: caps on this end's link, for when it's slower than the host's.
  • fallback_mbps (100): the link speed when nothing is advertised or measured.

Every estimate also carries the field names 0.1's placement used (estimated_total_usd, bandwidth_fees_known, cost_is_lower_bound, setup_download_s, assumptions, ...), so reports reading estimate receipts or offer.placement_estimate keep working.

Settings live in ~/.config/gipper/config.toml: hour_value_usd, failure_cost_usd ($1) and history_days (90).

How history changes placement

Consider two otherwise comparable offers: one has a lower hourly rate, while the other has a better host record. On a short job the expected cost of retrying a failed host can outweigh the hourly saving. On a long job, the saving accrues for more hours and can reverse the ranking.

This is a consequence of the score, not a fixed preference for a provider. A fresh ledger starts both providers with the same 10% failure prior and a 1.0 billing factor. Your qualifying receipts update those values; the job's placement hints and measurements determine the other inputs. Use gipper pod estimate to inspect actual candidate scores and their assumptions.

Memory

The ledger is the memory (~/.local/share/gipper/receipts), read back over history_days. gipper pod hosts shows it per provider and per machine. What counts:

  • good: run.start on the machine.
  • bad: a broken host: host.reject for a busy GPU, CUDA that won't initialise, ssh that never came up, a machine that died while starting, or a failed probe; or a connection lost before or during the job.
  • neither: a host that works but doesn't suit the job (run.Unsuitable, e.g. compute capability below the floor, or a client's runtime check); an error on this side (a local file that won't upload); a job that exits non-zero on a working host; a market with no stock. Rejects written before 0.2 have no kind and are classified by their message.
  • transfer speed: transfer receipts (bytes and seconds of real uploads and downloads).
  • compute time: run.end.compute_s from jobs that succeeded (older receipts: run.start → collect). Capped, failed or interrupted runs teach nothing about duration.
  • billing factor: spend.billed (from gipper pod reconcile, which the reap timer runs) against spend.

A connection lost mid-run is only noticed when it ends the run; while the log poll can't reach the host, gipper keeps waiting until the job's cap.

The optional probe

[placement]
probe_transfer_mb = 16          # MiB each way through the job's own ssh, before inputs
probe_timeout_s = 120           # total, at most 300
min_measured_upload_mbps = 10   # reject the host below these
min_measured_download_mbps = 10

It costs the rental time it takes, and a host it rejects is replaced like any other bad host. Use it when inputs are large and a slow path would waste the run. Its readings gate the host but don't feed memory: the timed real upload does that, for free.
